# Stage 4B2: durable account-origin foundation (local demo only)

Status: **EXTERNAL_TRUST_NOT_ENFORCED**. Durable consistency recovery is
implemented. Independent administrative authority is **NOT VERIFIED**.
Student admission and profile publication remain disabled. Nothing imports
this prototype into onboarding, HTTP routes, completion, workers or readers.

## Starting authority gap

Stage 4B1's `bootstrap.ts` keeps `requestId`, the newly created UID, Auth
creation time, random root binding, custom token, expected genesis and observed
Firestore creation metadata in process-local `requests` / `witnesses` maps.
After restart, stored fields alone cannot recreate the witnessed creation.
Stage 4B2 leaves that implementation and its meanings unchanged.

An unrestricted application Admin can replace genesis and user-tree records.
An Auth administrator can delete and import the same UID with the original
creation timestamp. An administrator can also restore custom claims. Matching
fields, hashes or an in-process signing key do not distinguish that history
from original creation. Firestore client rules do not restrict Admin writes.

## Actual boundary and explicitly missing boundary

The new prototype uses dedicated guarded clients for two real Emulator
projects, both on **127.0.0.1:18787**, default database:

* Application/Auth: `demo-edulience-phase2a` (Auth on 127.0.0.1:9099).
* Authority storage: `demo-edulience-origin-authority`.

These are separate storage realms, with deny-all browser rules in the authority
realm. They are **not** separate administrative identities. Emulator Admin
access can write either project. This process deliberately demonstrates that
limitation. No signature, injected provider, marker or hash can promote the
result to trusted authority. No credentials or signing keys are introduced.

Every result has `authority: "NOT VERIFIED"`, `admissionEligible: false` and
`publicationEligible: false`. Contracts name ORIGIN_ATTESTED and
ORIGIN_RECOVERED for the required vocabulary but reject attempts to emit them.

## Versioned contracts and storage

All records are schema version 1 and bind
`protocol: "durable-origin-stage4b2-v1"`. Typed, domain-separated hashes use
the existing strict canonical serializer. UID validation, malformed Unicode
rejection, defensive copies and exact property validation are reused.
Individual origin records are limited to 16 KiB; queued transaction writes
must fit 64 KiB and existing actual Firestore document budgets.

The authority realm contains:

| Path | Protocol semantics |
| --- | --- |
| `originProvisioningRequests/{requestKey}` | Create-only intent, original request and generated UID/incarnation |
| `originOwners/{uid}` | Bounded control derived from the complete event chain |
| `originOwners/{uid}/events/{sequence}` | Create-only, contiguous, predecessor-hashed phase events |
| `originAttestations/{uid}` | Create-only structural commitment, finalized atomically with its event |

The request accepts only `{requestId, identityForm}`; supported forms are
`ascii`, `unicode58`, `unicode128` for synthetic test identities. UID and a
256-bit random incarnation ID are generated by the operator harness, once
persisted as the winner of the request transaction. Request key is a typed
hash of the request ID. A repeated request with different contents conflicts.
There is no public preparation endpoint and no client-selected UID.

The intent binds UID, epoch 1, incarnation, exact request, root binding and
protocol. Root binding is derived from UID, epoch and incarnation. This
prototype never allocates another incarnation for an existing authority UID.

The commitment binds the complete intent, B1-compatible genesis hash, exact
Auth creation time, actual Firestore root/lifecycle/genesis/fence creation
metadata (seconds and nanoseconds), and a root-incarnation hash. All four
application documents are created by one transaction and must have the same
creation metadata. Visible timestamp fields cannot substitute for metadata.
The attestation additionally binds the authority realm and explicitly records
`trustBoundary: "EXTERNAL_TRUST_NOT_ENFORCED"`.

Only these application documents are created: `users/{uid}`, the Stage 4A
lifecycle, the B1 genesis, and the persistence-version-3 cumulative writer
fence. No Training performance evidence, assessment, profile generation or
completed session is fabricated. Compatibility tests use synthetic auxiliary
draft/activity/recommendation data, not accepted Training evidence.

## State machine and non-atomic boundaries

The append-only protocol phases are:

1. INTENT_RECORDED (request, control and first event atomically created).
2. AUTH_CREATE_STARTED (unique attempt recorded before any Auth mutation).
3. AUTH_CREATED (Auth creation and incarnation/protocol claims confirmed).
4. GENESIS_CREATE_STARTED (unique attempt before the application transaction).
5. GENESIS_COMMITTED (exact observed commitment recorded).
6. FINALIZED (attestation, event and control atomically written).

REVOKED is terminal from every existing phase. A seventh event slot is reserved
for revocation; ordinary provisioning cannot consume it. Reads replay the
entire at-most-seven-event chain, verify IDs/hashes/order/owner/bindings, compare
the derived control, and require the original attestation exactly when final.
Authority request, owner and first event creation metadata must also agree.
All event/attestation writes use transaction `create`, never replacement.

Operator-only API:

* `prepare({requestId, identityForm})`: persist intent, create Auth once, attach
  nonce/protocol claims, record confirmation, return a demo custom token.
* `finalize(verifiedToken, {requestId})`: derive UID from the verified demo token,
  check request/identity, create empty B1-compatible genesis, finalize commitment.
* `recover(verifiedToken)`: reread durable authority and actual Auth/application
  state; return consistency status without admission.
* `revoke(verifiedToken, {reason: "operator-demo"})`: append terminal denial.

Randomness, Auth RPCs and test boundary callbacks run outside transaction
reducers. Firestore retries replay deterministic proposed writes; they do not
repeat Auth creation. A same-request concurrent loser may receive a CAS/pending
error and retry later; it cannot create a different accepted UID. Identical
confirmed retries retain the original UID, incarnation and attestation hash.
Tokens are not stored in Firestore, files or logs; crash fixtures use private
IPC, not command-line token arguments.

| Interruption | Durable outcome and restart behavior |
| --- | --- |
| Before intent commit | No identity or records accepted; a new attempt is safe |
| After intent, before Auth-start checkpoint | Resume same stored UID |
| After Auth-start checkpoint, before Auth RPC | Pending, controlled recovery required |
| After Auth creation, before claims or confirmation | Pending, controlled recovery required |
| After confirmed Auth checkpoint | Resume exact UID; no repeated create RPC |
| After genesis-start checkpoint, before/after application commit | Pending, controlled recovery required; do not infer an unacknowledged outcome |
| After genesis commitment checkpoint | Verify and finalize exact commitment |
| After finalization, before response | Recover identical stored commitment and attestation after a fresh process |
| Final attestation transaction fails | No partial attestation/event; prior committed genesis remains intact |

Ambiguous states deliberately have no automatic adoption/repair API. A future
controlled operator protocol must establish external authority before choosing
recovery, cancellation or cleanup. An Auth RPC error retains its intent and
may leave a reserved UID; it never silently substitutes another identity.

## Result states and revocation

* PROVISIONING_PENDING: incomplete protocol or ambiguous Auth/genesis outcome.
* ORIGIN_UNVERIFIED: authority missing, malformed, substituted or unreadable;
  source/lifecycle cannot be verified. No fallback to application genesis.
* ORIGIN_REVOKED: terminal stored denial or positively observed Auth/root/
  lifecycle/epoch mismatch, with confirmed durable revocation.
* EXTERNAL_TRUST_NOT_ENFORCED: all finalized structural commitments match,
  including after process restart; administrative provenance remains unproven.
* ORIGIN_ATTESTED / ORIGIN_RECOVERED: **never emitted by this demo**.

Recovery never treats generic network/parse failure as permission to recreate
an account. Mismatch-triggered revocation must commit or returns unverified.
Revocation CAS retries are bounded by the monotonic creation phases and reread
the winning state. Existing revocations are never replaced, even for a
different later reason. Cooperating API calls cannot revive a revoked UID.

Lifecycle closure, root recreation and epoch changes are checked on recovery
and confirmed retries. Cross-project/Auth operations are not atomically
coordinated: a concurrent revocation may leave orphaned Auth/genesis artifacts,
but cannot create admission or revive authority. Deletion coordination with
all application writers has not been implemented. An unrestricted Admin can
roll back or delete the entire authority ledger/tombstone, so monotonicity is
an API guarantee within the stated test boundary, not an IAM guarantee.

## Attacks and interpretation

Tests perform real demo Auth import with preserved creation time. Without the
incarnation claim it produces durable revocation. With **both** original time
and claims restored it can be structurally indistinguishable; the result
still remains EXTERNAL_TRUST_NOT_ENFORCED. This is an expected demonstration
of the unresolved Auth administration gap, not authenticated origin recovery.

Wrong-owner/epoch/altered attestations fail validation. Missing attestations
do not adopt a user-tree marker. Browser reads and writes to the authority
realm are denied. A privileged Admin can delete and recreate an identical
attestation, or reconstruct a self-consistent ledger; hashes alone cannot
detect that provenance attack. The prototype never labels it trusted.

## Required independently enforced production design (not implemented)

Before any future trusted-state branch:

1. Place authority in an independently administered project/database/service.
   Application Admin and Training writer identities must have no authority
   write/delete/replace permissions, no authority credential access, and no
   ability to impersonate the authority service or modify its IAM/deployment.
   Firebase client rules are insufficient; Admin IAM must enforce the boundary.
2. Use a separately managed provisioning identity for Auth mutations and origin
   finalization. Restrict import/delete/custom-claim operations; existing
   application credentials must not recreate an account with restored claims.
   Auth timestamps/claims are not non-reusable Firebase incarnation witnesses.
3. Independently authenticate authority-service responses and bind each read
   to expected project/protocol/UID/epoch/incarnation. Store immutable creation
   facts and revocations in the protected boundary; protect backup/restore and
   anti-rollback guarantees. No caller-selected database/provider is proof.
4. Define audited operator recovery for ambiguous provisioning, permanent UID
   exclusion/tombstones, account deletion, retention and service outages.
   Hash-chain continuity does not protect against a privileged complete rollback.
5. Integrate lifecycle fencing into **every** completion, worker, publisher,
   root/profile writer, deletion and applicable privileged auxiliary writer.
   Revalidate independently verified authoritative bootstrap/inventory and
   revision admission; origin consistency is not complete inventory authority.
6. Review IAM with an independent owner and test real denied administrative
   operations in a separate non-student environment. Emulator tests cannot
   prove any of these production permissions.

No production IAM changes, onboarding changes or writer activation are part
of Stage 4B2. Protected-owner Training integration is a later dependency.

Existing v1 completed receipts, original `profileRevision`, v2 accepted receipts,
their identical-retry recovery, outbox records and source fingerprint protocols
are not modified or reinterpreted. The new protected genesis is deliberately
incompatible with uncoordinated v1/v2 writers and existing shadow workers.
Tests require those calls to reject without changing receipts, evidence or
quota counters. Origin finalization does not reserve or complete Training.

## Running isolated validation

Use the pinned Node 24 runtime and `scripts/run-sanitized.mjs`. Start existing
demo Auth/Firestore Emulators with the sanitized existing completion launcher;
then run `scripts/run-stage4b2-emulator-tests.mjs --tools-dir <isolated-tools>`
through the sanitized wrapper. Run suites that change Emulator rules serially.
The runner requires both loopback services and fails when either is absent.
It uses explicit demo projects; there is no production fallback. The dedicated
Stage 4B2 config documents the two-project setup; tests load the complete
unchanged B1 app rules and new authority deny-all rules, then restore the local
owner-supplied app rules. No deployed rules are read or changed.

The new Emulator suite exercises real subprocess exits at ten boundaries,
Firestore transaction retry/abort, retained identity, identical/conflicting
retry, token ownership, two-store tampering, Auth import, root recreation,
revocation, Unicode and auxiliary compatibility. Existing Stage 1-4B1 suites
remain separate compatibility checks. Build output is isolated under ignored
`dist-stage2`; the active backend metafile must contain zero scalability inputs.

This foundation proves durable protocol consistency within the demo boundary.
It does not prove independent trust, production capacity, student admission,
successful publication or production readiness.
